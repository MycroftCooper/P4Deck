# P4Deck 技术架构

> 文档编码：UTF-8  
> 架构状态：核心分层已落地

## 技术栈

- 桌面框架：Tauri 2
- UI：React 19 + TypeScript + Vite
- 桌面后端：Rust
- P4 接入：用户安装的官方 `p4` CLI
- 包管理：pnpm
- 服务端状态：TanStack Query
- 轻量本地状态：Zustand

## 选择原因

Tauri 使用系统 WebView 和 Rust Host，相比捆绑 Chromium 的方案更符合 P4Deck 对启动速度、内存和安装包大小的目标。React 生态具备成熟的虚拟列表、Diff、编辑器和无障碍方案。Rust 负责受控进程执行、并发、缓存、安全策略和输出解析。

首版通过官方 `p4` CLI 与 Helix Core 通信，优先使用 `p4 -ztag -Mj` 获取逐行 JSON 结构化输出，从而兼容用户已有的 P4CONFIG、P4TRUST、P4TICKETS、Broker、Proxy、SSO/MFA 和服务器策略。未来可在同一接口后增加 P4API Adapter。

## 分层与依赖方向

```text
React Features
  ↓
Backend Contract
  ↓
Tauri IPC Commands / Events
  ↓
Rust Application Services
  ↓
P4 Repositories
  ├─ Command Builder
  └─ Output Parser
  ↓
P4Runner
  ↓
官方 p4 CLI
```

依赖只允许从上向下：

1. `ipc` 只负责协议接入、状态获取和调用应用服务，不实现业务规则。
2. `app` 编排用例，不拼 P4 参数、不解析 P4 输出。
3. `p4/*/repository` 将领域请求映射到 P4 调用。
4. `command` 只构造结构化命令、参数和标准输入，不启动进程。
5. `parser` 只把 P4 输出转换为领域对象，不调用 Tauri、SQLite 或进程。
6. `runner` 不认识 CL、Shelf、Stream 等业务概念，只负责安全执行、流、取消、超时、回收和日志。
7. `persistence` 不依赖 UI 或 Tauri Command。

凭据数据流固定为：结构化请求 → `security` 策略校验 → 移除继承的 `P4PASSWD/P4TICKETS/P4TRUST` 并仅恢复受控路径环境 → 创建子进程 → stdout/stderr 逐行及 JSON 字段脱敏 → `OperationEvent`/`OperationResult` → LogStore/Journal 写入二次脱敏 → 查询与诊断导出末端兜底。任何事件广播都发生在脱敏之后。`CredentialRedactor` 不实现 Clone/Debug/Serialize；显式已知 secret 只存在于单次命令生命周期。受控 Login 密码只经 stdin 使用，调用结束后立即 zeroize。

## 前端模块规则

- `app` 可以组合多个 Feature，但 Feature 不反向依赖 `app`。
- `features` 之间默认不直接引用；跨功能协作通过应用层状态或共享契约完成。
- `infrastructure/backend/contract.ts` 是前端访问桌面后端的唯一抽象。
- `tauriBackend.ts` 只做 IPC 映射，`mockBackend.ts` 只做浏览器开发模拟，两者实现同一契约。
- `shared` 只能存放无明确业务归属、可被多个模块复用的内容，禁止成为杂物目录。
- UI 组件不得直接调用 `invoke()`，也不得自行拼接 P4 命令。

## P4 调用边界

### 文件 Lock/Unlock 写边界

文件锁只经 `FileLockService` 的 `preflight_file_lock` → `confirm_file_lock` 执行。`p4/locks` 分为 command/parser/repository：命令层校验显式非递归文件并转义 literal filespec，解析层只消费 tagged JSON，Repository 负责 `info/where/fstat -Ol/protects -M/lock/unlock`。通用 `FileAction`、Terminal 与 generic `run_p4` 不得执行 lock/unlock。

预检快照包含完整 Profile/Connection/Workspace/generation、操作类型，以及每个文件的 depot/client/local mapping、opened action、CL、filetype/`+l`、权限、我方/他方锁 owner 与 other-open。一次性 token 与 SHA-256 digest 绑定整个排序文件集合；确认进入同 Server mutation lane 后重查同一快照，任一 TOCTOU 漂移即拒绝。批量修改逐文件执行并保留 partial/cancelled/unknown，不自动回滚；最终状态仅由 tagged `fstat -Ol` 验证。P4Deck 不提供管理员强制解锁 API；他人锁只返回 blocker 并引导联系管理员，由应用外工具处理。

Workspace/Pending 聚合查询复用相同字段模型。`otherLock`/`otherOpen` 基础字段只是计数，因此查询还显式请求有界 indexed owner 字段，UI 不得把计数当用户名；超过展示上限仍保持保守状态。修改结束失效 Workspace、Opened、Pending、Search 和 Review 相关缓存，前端按连接 key 丢弃迟到结果。

### Stream 切换写边界

基础 Stream 切换由独立 `StreamSwitchService` 编排，不复用通用 Terminal/`run_p4` 写入口。预检依次读取 `info`、Client spec、目标 Stream spec、protects、opened、resolve preview、reconcile preview 与 sizes，并生成不可变 `StreamSwitchTargetSnapshot`。一次性 token 将完整 profile/连接/Workspace/generation、源目标 Stream、执行模式以及 Client/Stream/risk digest 绑定；确认进入同 Server mutation lane 后重新执行同一检查，任一漂移即拒绝。

执行只允许非 force `p4 client -s -S <stream> <client>`；默认到此结束且不修改文件。用户另行选择同步且确认风险时，目标 Stream 验证成功后执行非 force `p4 sync //client/...#head`。最终再次读取 Client spec；成功后推进 Context generation 并清除 Workspace、Streams、Pending、Submitted、Search、Depot 相关缓存/确认。失败、取消和未知结果不调用 `p4 switch`、`clean`、`revert` 或自动回滚，返回已知 Stream/同步边界和恢复预检入口。

Stream Graph、Branch Mapping、Stream spec 写入及管理员能力不在该服务职责内。

### 文件审查只读边界

Diff、History 与 Revision Graph 不接受裸 path IPC。每次请求包含 `FileReviewScope` 与当前 runtime identity；Rust 在执行前后都复核活动 profile/context generation，拒绝跨连接、跨 Workspace 或返回途中发生漂移的结果。引用为 `Workspace | Have | Head | Revision(n) | Shelf(changeId)` 判别联合；Shelf 由后端权威生成 `depot@=<change>` 并通过参数数组读取，前端不能把 `@=` 字符串塞进 revision 或裸 filespec。

Depot 文本通过 Runner 参数数组执行 `print`，Workspace 通过当前 Client 的 `fstat clientFile` 后受控读取。Shelf 详情通过 `describe -s -S` 加逐文件 `fstat -Rs -e` 获取，缓存键绑定 Server/User/Client/generation/change，TTL 30 秒；每页 1～500、总量 10,000，显式刷新绕过缓存。Shelf 内容只对文本执行 `print -q depot@=change`；binary、symlink、delete/missing 和超过 4 MiB 的内容只返回元数据与明确原因。filetype 决定文本/binary/symlink 分支，扩展名只用于 UI，不参与安全判断。单侧文本 4 MiB/100,000 行、Diff 8 MiB、History 500/页、Graph 2,000 revision 是硬上限；所有截断进入契约。History cursor 和 30 秒/128 项审查缓存均绑定完整 scope/file/selector，显式刷新绕过缓存。

Graph 数据源是 `filelog -i -l -t`：同 depot path 相邻 revision 形成 `revision` edge，`how/file/srev/erev` 形成有方向的 integration edge。`from` 关系由 related revision 指向当前 revision，`into` 反向；缺失端保留占位节点，循环/重复边按完整 edge identity 去重。前端只渲染该模型，不自行推断 merge。

文件审查的前端请求所有权由 `reviewRequests.ts` 统一管理。owner identity 固定包含 Connection（Server/User/Client/Workspace）、活动 Profile、Context generation、`FileReviewScope`、当前 tab、请求种类，以及该请求实际使用的 left/right reference、node/edge identity、cursor 或 expand target；每个通道再附本地单调 sequence。路径、scope、tab、profile/generation、selector、node、cursor 或组件生命周期变化时，旧 lease 的 `AbortController` 会触发根 `operationId` 的 `cancelOperation`，且旧 lease 不能提交 data/error/loading 或写 React Query cache。数据本身带 owner envelope，因此 prop 已变化而 effect 尚未运行的同一帧也不会显示旧 Depot 内容。

Graph 首屏、分页、跨文件占位节点展开和节点 Diff 使用同一 owner 规则。分页 cursor 分为 pending/consumed：同一 cursor 不会并发或重复消费；失败保留可信图并允许重试；节点按 ID、边按 source/target/kind/relationship/revision 范围的语义 identity 合并，`missing` 节点只允许被真实节点升级。History 分页采用相同 cursor 纪律并按 depot path + revision 去重。

Rust `P4Runner::begin_operation_group` 在整个审查用例存活期间持有根 cancellation token，子命令使用 child token。这样取消不只杀死当前 `fstat/filelog/print`，也覆盖两条子命令之间的空窗，并在最终 generation/scope 复核和 cache put 前再次拒绝取消；取消结果不进入 30 秒审查缓存。

以 CL 查询为例：

```text
ChangelistPage
  → Backend.queryChangelists
  → ipc::commands::query_changelists
  → ChangelistService::query
  → ChangelistRepository::query
  → command::query_invocation
  → P4Runner::run
  → parser::parse_change_events
```

新增 P4 功能时，应在 `p4/<业务>/` 下建立独立的 `command`、`parser` 和 `repository`，不能把所有命令堆回 `runner.rs`，也不能在 `app` 或 `ipc` 中出现参数数组。

Pending CL 遵循同一边界：`query_pending_changes` / `mutate_pending_change` 以及 `preflight_move_files` / `confirm_move_files` 的 IPC 只转发，`ChangelistService` 负责当前 Connection 作用域、写前校验、一次性 token、局部失效和受影响对象刷新，`ChangelistRepository` 负责 `changes/opened/change -o/describe -S/change -i/reopen/where` 调用及结构化映射。创建/编辑/删除仍走基础写契约；菜单、键盘与拖拽移动复用同一 MoveFiles 状态机。确认阶段逐文件执行并复核最终归属，允许表达 partial/cancelled/failed；前端只依据来源/目标 `refreshedChanges` 局部合并，失败或刷新不确定时保守失效相关查询。

Pending 读契约现为 `PendingChangeQuery → PendingChangePage`。Default 通过 `defaultChange` 单独返回，numbered 项通过 `items/nextCursor/hasMore` 增量读取。首次查询在 Rust 侧建立 60 秒、最多 32 项的有界不可变快照；opaque cursor 含随机 snapshot ID、offset、query fingerprint、完整 connection fingerprint、connection generation 与独立 pending generation，并额外在缓存中核对“是否由本快照真实签发”，因此客户端改写 Base64 载荷不能伪造下一页，同时网络失败仍可用同一 cursor 重试。连接切换和任何可能改变 Pending 的成功写操作会清空快照并递增 pending generation；旧响应还需通过前端 request generation 才能落入页面。

Pending 数据与 form 规则：

- 查询作用域必须同时绑定当前 User 与 Client；Default 使用 ID `0`，编号 CL 不得因忽略 `opened.change` 回落到 Default。
- Description、Jobs 和 shelved files 来自 Server 返回；缺少的时间、Client Path、Revision 或 Workspace state 使用缺省值，不补造事实。
- Description 的每一行都作为 form continuation 缩进；Jobs 只能是单行 token，并在 `change -i` 前做精确存在性预检。
- Pending Edit 的 `jobs` 是完整替换列表而非可选 patch；调用方必须显式传入当前列表，清空时明确传 `[]`，避免漏字段导致静默解除 Job 关联。
- P4 2026.1 的 form stdin 不与全局 `-Mj` 混用：读操作使用 `-ztag -Mj`，`change -i` 使用 Text stdin，再从受控回包解析创建编号。
- 删除“空 CL”要求 opened files、shelved files、Jobs 全部为空。P4 对带 fix 的 `change -d` 可能输出拒绝文本却返回进程码 0，不能只以 exit code 判断业务前置条件。

Submit 使用独立的确认状态机，不复用泛化 FileAction：

- `SubmitPreflight` 返回结构化 blocker/warning、当前 Server/User/Client/Workspace/Context generation、完整 CL/文件摘要、一次性 token、TTL 及 operation/log 引用。原始 P4 stderr 只在 Repository 内用于分类并进入脱敏 Log，不作为前端判断协议。
- 预检通过 Pending 快照、`fstat`、`protects -M` 和 Job 查询检查空描述、空 CL、unresolved、out-of-date、锁/独占打开、写权限、Shelf 与 Job；不能从客户端可靠得知的权限兼容性、文件状态或 server trigger/job 策略必须标记 `unknown` warning。
- token 仅保存在进程内，默认 120 秒且只能消费一次；它绑定 Connection/Workspace、Context generation、change ID、Description/Jobs/Shelf、文件集合与 fstat/权限摘要。连接切换后即使切回相同文本配置，generation 变化也会令旧 token 失效。
- 确认阶段先占用 Runner 的单 Server mutation lane，再重新读取并比较快照；只有完全匹配且 blocker 仍为空才执行单条 `p4 submit -c <change>`。该 lane 覆盖“复核→执行”，防止本应用内其他写操作插入；外部客户端竞争仍由 Helix Core 的原子 Submit/锁规则最终裁决。
- `SubmitResult` 只暴露 `submitted/rejected/failed/cancelled/unknown`、结构化 failure code、operation/log 关联和刷新建议。取消、超时或进程级不确定失败要求刷新 Pending/Submitted/Workspace 后再操作，不能自动重放。
- `FileAction::Submit` 与 TypeScript `P4FileAction` 的 `submit` 已移除；Mock、泛化 `performFileAction` 和 GUI 来源的通用 `run_p4` 都不能执行 Submit。用户显式打开的受控 P4 Terminal 仍保留终端命令语义。

Shelf / Unshelve / Resolve 使用同一确认模型：

- `app/confirmation.rs` 提供 Submit 与 BE-004b 共用的一次性进程内 token store；各业务 record 绑定目标快照、内容摘要与到期时间，消费后不可重放。
- Shelf 详情读取使用独立的服务端快照 cursor，不与写操作 confirmation token 混用。首屏读取并排序完整 Shelf 元数据后冻结快照；cursor 携带 snapshot/cursor ID、offset 及查询/连接/双 generation 指纹，但只有 cursor ID 与服务端 issued offset 映射完全一致且未消费时才有效。快照 120 秒过期、最多 32 份；30 秒内重复首屏可复用同一冻结数据并签发新的 continuation。外部数据变化不会改变已冻结页面，因此不会跨页重复/漏项；显式刷新、本应用 mutation 或连接代次变化使旧 cursor 明确失效。
- Shelf 预检固定编号 CL 与显式文件集合，比较 opened/shelved 归属、`fstat -Ol` 内容摘要、实际 Workspace 内容哈希、锁与 `protects -M`。首次创建、选中文件覆盖更新和选中文件删除分别建模；覆盖子集使用 `p4 shelve -f -c <CL> <files>`，避免 `-r` 删除未选 Shelf 文件。
- Unshelve 预检通过目标 Client spec 构造隔离 Context，支持当前或其他 Workspace、Default/编号目标 CL；`where`、opened/fstat、`diff -sa/-se`、锁、权限与 `unshelve -n` 形成结构化映射和风险。执行永不默认附加 `-f`。
- Resolve 仅把 `fstat.unresolved > 0` 且 dry-run 成功的文件标为可执行；逐文件策略映射为 `-am/-ay/-at`，`mergePreview` 仅供预览。执行后再次读取 unresolved，仍有冲突时返回 blocked，复核失败时返回 unknown，不伪造 resolved。
- Shelf/Unshelve/Resolve 的确认阶段先占用同 Server mutation lane，再完整重查并比较 Connection generation、Workspace、CL、文件集合、shelf/server digest、本地内容与风险摘要。结果携带 operation/log 关联、逐文件终态和保守刷新建议。
- Shelf、Terminal、P4 Log 等独立窗口沿用 Dock 的 `panelKind`、`p4deck.panel.<id>` 参数和版本化 `p4deck.nativePanels` 恢复路径；Rust `open_panel_window` whitelist 只接受已注册 kind 与安全 ID，同 label 重开只聚焦已有窗口。`window_placement` 在应用数据目录统一保存所有 panel 的普通 bounds/maximized，并按当前 monitor 几何校正拔插多屏后的越界状态；业务页面不得自建并行坐标存储。
- 应用级入口使用 `app/commands/catalog.ts` 作为稳定命令 ID、名称、快捷键和禁用原因的单一事实源；应用菜单只发送经白名单验证的 command ID，前端执行前再次检查环境。浮窗 deep link 的 runtime binding 只包含 profile、generation 与不透明 connection token，真正 P4 Context 仍由受控 Runtime 提供。
- 泛化 `ClAction` 不再包含 MoveFiles/shelve/unshelve；`PendingChangeMutation::MoveFiles` 的 IPC、`FileAction::MoveToChangelist` 与 GUI 来源的通用 `run_p4 reopen` 均只返回“必须走预检确认 API”。显式 Terminal 继续保留原始 P4 命令语义。

Rename/Move 使用独立单文件确认模型：

- `p4/rename/{command,parser,repository}.rs` 负责参数数组、`where/fstat/change -o` 解析和真实 `p4 move`；`app/rename_service.rs` 负责映射、opened、目标存在性、目标 CL、Context generation/profile、一次性 token、preview digest、mutation lane 复核、结构化结果和缓存失效。
- 本批只允许当前 Workspace 内的单个受控本地文件，source 必须 opened for `edit/add`；目标只能是同一 Client mapping 中不存在的文件，目标 CL 只能是 Default 或当前 User/Client 的既有 Pending 编号 CL。目录、跨 Workspace、覆盖及不存在父目录不扩展成隐式递归或创建行为。
- Windows 仅大小写改名在没有可靠临时名事务/回滚前固定为 blocker。`FileAction::RenameMove` 已删除，GUI `run_p4 move` 被拒绝；工具栏与右键菜单只进入同一个 `RenameDialog` Preview → Review → Confirming → Result 状态机。
- token 绑定 active profile、Context generation、source/target depot+client+local 映射、source opened state、目标 CL 与 preview digest；确认在单 Server mutation lane 内重查，重放、过期或任何漂移均拒绝。单文件非零退出没有“部分成功”集合，按 failed/cancelled/unknown 返回并要求刷新两端 Workspace/Pending 状态。

## 计划模块

- `connection`：连接配置、trust、登录、SSO/MFA。
- `workspace`：Client Spec、Workspace 发现和切换。
- `status`：Opened、Reconcile、Out-of-date 聚合与缓存。
- `changes`：Changelist、Shelve 和 Submit。
- `files`：Depot 浏览、文件历史、内容和 Diff。
- `operations`：队列、进度、取消、重试和操作记录。
- `terminal`：按需创建的 P4 专用命令行会话、上下文继承、输入输出流和中断。
- `logs`：结构化 P4 日志、脱敏、环形缓冲、分段落盘、过滤和自动展开事件。
- `settings`：应用设置、工具路径、快捷键和安全凭据引用。
- `workspaces`：受限本地树扫描、Client View 映射和 P4 状态叠加。
- `depots`：`p4 dirs/files` 懒加载的服务器资源树。
- `files`：状态矩阵、Sync/Edit/Add/Delete/Revert 用例和局部刷新。
- `diff/history/revision_graph`：文件内容比较、filelog 解析和 integration 关系图。

## 安全约束

1. React 不得获得任意 shell 权限。
2. Rust 只执行已经建模和审核的 P4 命令。
3. 参数使用 `Command.arg()` 独立传递，禁止拼接 shell 字符串。
4. 密码通过标准输入传递，禁止 `-P password` 和交互式 `P4PASSWD`。
5. 默认复用用户 ticket 和 trust 文件。
6. 如果保存秘密，只能使用 macOS Keychain 或 Windows Credential Manager。
7. 日志必须脱敏 ticket、密码、登录输入和用户路径。
8. 通用 Terminal 的命令识别基于 token/全局参数位置，不使用子串猜测；认证命令和 `set/configure` 在 spawn 前拒绝。官方 CLI 语义中 `p4 tickets` 会列出票据文件内容，`p4 passwd` 修改密码，`p4 set` 可列出/写入 P4 变量，`p4 configure show/set/history` 可读取/修改服务器配置，因此均不属于通用 Terminal 边界。
9. 裸 digest 不是凭据判据；ticket token 只通过被阻止的命令、显式已知 secret 或 Ticket/Authorization 等上下文识别。

命令风险核对依据：Perforce 2026.1 官方文档的 [`p4 tickets`](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_tickets.html)、[`p4 passwd`](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_passwd.html)、[`p4 set`](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_set.html) 与 [`p4 configure`](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_configure.html)。
8. 限制输出大小、执行时间和每个 Server 的并发数量。
9. 服务器字符串和文件路径一律作为不可信输入。

## 性能策略

- 启动先展示带时间戳的缓存快照。
- Workspace 当前目录做一次非递归本地扫描，并与 `fstat/opened/resolve preview/reconcile preview/ignores` 按规范化 Client Path 合并；不跟随 symlink/reparse point，单次最多返回 10,000 项。
- 通过 Tauri Channel 分批推送大量记录。
- CL、CL 文件、Depot、历史、日志和查询结果从首个实现开始必须虚拟滚动；禁止先全量渲染再优化。
- Rust 通过 Channel 分批发送记录，前端按稳定 ID 合并；单批大小和发送频率需要基准测试。
- 搜索条件优先下推到 P4 CLI；本地二次过滤放入 Worker 或 Rust 后台任务，不能阻塞 UI 主线程。
- 每次查询分配 Generation/Request ID；过时响应必须丢弃，切换条件时取消可取消的旧任务。
- 合并短时间内重复刷新请求。
- 每个 Workspace 的修改操作进入串行队列。
- 只读查询受控并发；长任务提供进度和取消。

### Workspace 状态契约

`WorkspaceListing` 是 Workspace 浏览的完整响应：`items`、查询级 `completeness/errors`、P4 `operationIds`、`truncated/safetyLimit` 和 `cacheFreshness`。每个文件的 `WorkspaceFileStatus` 把 opened action、reconcile candidate、sync、resolve、local、mapping、move 对端和 ignore provenance 保持为正交字段；`primary` 只提供稳定的首要展示状态。

分类优先级固定为 unresolved/conflicted → opened edit/add/delete/move → reconcile edit/delete/add → out-of-date/not-synced → controlled/unknown。只有 `reconcile -n` 的 add 证据才产生 untracked；只有 `p4 ignores -v -i` 的匹配才产生 ignored，并保留规则、来源文件和行号。P4 子命令或本地元数据失败不会抹掉其他证据：响应标为 partial 并返回结构化错误；没有权威证据的既有本地文件保持 unknown。

缓存键包含 Server/User/Client、规范化目录、查询类型和 schema version；15 秒 TTL、512 条/16 MiB 上限，并发请求合并。手动刷新先按目录失效，修改操作按受影响路径失效，连接 generation 变化清空旧状态。一次查询的 operation 前缀派生 `:fstat/:opened/:resolve/:reconcile/:ignore-N`，取消前缀会终止整组子命令。前端只渲染后端返回的证据，partial/error 以列表提示和完整 title/读屏文本呈现，不为单行追加 P4 请求。

## P4 批量调用与并发策略

文件 Action 不允许为每个文件各启动一个 `p4` 进程。批量策略统一由 `p4/files/command.rs` 和 `P4Runner` 执行：

1. 最多 128 个且参数总长度不超过 24 KiB 的 filespec，作为同一条 P4 命令的参数一次提交，例如 `p4 sync file1 file2 ...`。
2. 超过上述阈值时，改用全局参数 `p4 -b 128 -x - <command>`，通过标准输入逐行传递 filespec。这样既保留 P4 的批处理能力，也规避 Windows/macOS 的命令行长度限制。
3. `move`、`integrate`、`copy` 等具有源/目标配对语义的命令不得使用通用 `-x` 展平，必须保留为单次配对调用。
4. `sync`、`shelve`、`submit` 支持 P4 原生 `--parallel`，但只能显式启用，线程数限制在 2–4，固定 `batch=8,min=9`。默认不擅自启用，因为服务器需要配置 `net.parallel.max`，盲目增加线程可能降低性能。
5. 同一个 P4 Server 最多同时运行 4 个 P4 进程；修改命令每个 Server 严格串行。未知命令按修改命令处理，避免新命令绕过限流。
6. 排队、开始、工作项完成和进程结束分别推送 0、2、2–95、100 的进度。P4 CLI 没有覆盖所有命令的统一字节级进度，因此当前百分比统一表示已完成工作项。`p4 -I` 仅覆盖部分命令，而且需要与 JSON Lines 输出做版本兼容验证，完成兼容矩阵前不作为默认进度源。
7. 单次命令捕获的输出上限为 64 MiB，超限会取消子进程；所有命令仍受超时和用户取消控制。

## P4 命令行与日志边界

- 内置命令行是 P4 专用会话，不是默认开放的通用系统 Shell。
- 命令行和日志 UI 默认不创建、不渲染；用户打开或自动展开时才挂载视图。
- Terminal 只在后端策略通过并完成调用后写入非敏感历史；旧历史在读取时过滤并重写。被阻止命令只显示固定安全原因与“打开连接设置”，不显示原始参数。
- 旧版 SQLite 日志在启动时执行幂等、事务化原地脱敏；无备份副本以免复制秘密，压缩失败不影响读侧/导出侧继续脱敏。Operation Journal 不保存命令、stdin 或自由文本错误，旧 workspace 字段仍在查询时再次脱敏。
- 底层操作记录始终结构化采集，但采用固定内存上限和磁盘轮转。
- GUI 操作与用户终端命令共用命令执行器、取消令牌和脱敏规则，但使用不同来源标识。
- Warning/Error 通过事件通知 UI；是否自动展开由用户设置决定，事件不得直接抢夺输入焦点。

## 备选方案

| 方案 | 决策 | 原因 |
|---|---|---|
| Electron | 保留备选 | 生态成熟，但基线资源占用与目标不符。 |
| Flutter | 暂不采用 | Diff、编辑器和 Web UI 生态复用较弱。 |
| Qt/C++ | 暂不采用 | 跨平台 UI 迭代和维护成本较高。 |
| 直接绑定 P4API | 后续评估 | 涉及 ABI、打包、升级和许可证评估。 |
