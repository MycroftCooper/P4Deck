## 2. 状态口径

| 状态 | 定义 |
|---|---|
| 已完成 | 有前后端或明确单端实现，并有自动化测试或可重复验证证据；在当前约定范围内可用 |
| 部分完成 | 已有 UI、契约或底层能力，但用户流程、异常处理、平台验证或验收证据不完整 |
| 未开始/未完成 | 没有可用实现，或只有文档规划、占位入口 |
| 阻塞 | 会阻止当前阶段构建、集成或验收的问题；未来发布要求不自动升级为当前阻塞 |

功能是否“完成”以用户闭环和验收证据为准，不以文件、按钮或接口是否存在为准。

## 6. 当前项目结构与职责

```text
P4Deck/
├── src/                         React 前端
│   ├── app/                     应用装配、Dock、Shell、全局 Hook 与样式
│   ├── features/                按业务能力组织的页面和交互（组件在各自 components/）
│   │   ├── browsers/            Preview、Diff、History、Revision Graph、Streams
│   │   ├── changelists/         Pending 与 Submitted 工作流
│   │   ├── companySubmit/       企业化提交流程
│   │   ├── files/               Workspace/Depot 浏览、地址、文件动作
│   │   ├── settings/            连接、主题、语言与 UI 偏好
│   │   ├── tools/               P4 Terminal 与 Log
│   │   ├── workspaces/          Workspace 列表与详情
│   │   ├── search/              全局搜索
│   │   └── swarm/               Swarm 集成入口
│   ├── infrastructure/backend/  Backend 契约及 Mock/Tauri 适配器
│   └── shared/                  共享契约(contracts.ts)、缓存、i18n 和无业务归属工具
├── tests/                       非单元测试资产
│   ├── browser/                 Playwright 端到端 spec
│   └── qa/                      QA 写域：批次验收夹具、视觉审计与证据
├── src-tauri/src/               Rust 桌面后端
│   ├── ipc/                     Tauri Command 边界
│   ├── app/                     应用服务与用例编排
│   ├── domain.rs                领域模型
│   ├── p4/                      P4 Runner、Context 与业务 Repository/Parser
│   └── persistence/             会话 JSONL 日志与 SQLite Journal 等本地持久化
├── ForAIDoc/
│   ├── PM/                      范围、路线图、状态与验收口径
│   ├── Coder/                   架构、实现说明与开发环境
│   └── Designer/                体验与界面规范
├── scripts/                     环境检查、安装辅助、构建门禁与本地 p4d Fixture
├── tools/dsh-p4deck-board/      DSH 工作流看板插件
├── artifacts/                   构建与验收产物（git 忽略）
├── .local/                      本机运行时安装（git 忽略）
├── assets/                      品牌源素材
└── public/                      Web/Tauri 静态资源
```

### 结构治理规则

1. PM 文档定义“为什么做、做什么、优先级、完成标准”；技术文档定义“怎么做”；设计文档定义“如何交互与呈现”。
2. 新业务能力优先进入 `src/features/<domain>`（React 组件放该域 `components/`）；跨功能契约进入 `src/shared/contracts.ts`；外部系统适配只进入 `infrastructure`。
3. Rust 的业务参数构造和解析放在 `p4/<domain>`；`ipc` 不承载业务规则，`runner` 不认识具体业务对象。
4. 功能状态变化先更新本文件，再同步路线图、实现说明和 README，避免多个“当前状态”互相冲突。
5. 完成项必须附验证证据；只有 Mock 演示、只有 UI 或只有底层命令时，一律记为“部分完成”。

## 8. 风险与待决策

| 风险/决策 | 影响 | 当前建议 |
|---|---|---|
| 只有本地 Git 基线、没有 remote 执行 | 本机可回滚、可运行本地门禁，但无法证明异机恢复 | 当前先做离线配置备份与本机恢复演练；remote/CI 留给后续发布阶段，不阻塞本机私用 |
| 文档描述曾领先/落后于代码 | 进度判断失真 | 本文作为状态单一入口，其他文档只保留稳定规范 |
| 第一轮原生点击不完整，最终 exe 尚未复验 | 可能遗漏普通 Lock/Unlock 回归、WebView2、退役菜单仍显示、Settings 连接管理、窗口和焦点问题 | 新 build 先确认管理员入口与原生顶栏菜单消失、Settings Profile 管理及普通锁流程可用，再按剩余有限清单逐项留证；已通过项不重复，浏览器证据不替代 |
| 本人 Server 策略与 fixture 不同 | 认证、权限、trigger 或文件类型可能改变行为 | 先只读连接，再只在专用测试路径演练 mutation；不对生产数据做故障注入 |
| 配置或写操作中断 | 可能出现 unknown 状态或本地恢复困难 | Journal/刷新/人工复核、离线备份和恢复已在 fixture 原生验收；实际 Server 上的 SSO/MFA 与权限仍由 WIN-P0-03 验证 |

## 9. 文档维护机制

- 每次合并会改变用户可见能力的工作后，更新“功能进度台账”和“最近盘点”日期。
- 每次本机验收后检查 P0/P1/P2 状态、证据绑定和路线图阶段判断。
- 需求新增或降级时，先修改《核心功能基线》或《开发路线图》，再进入开发。
- 架构边界变化同步更新《技术架构》；实际实现范围同步更新《核心功能实现说明》；交互变化同步更新《体验与界面规范》。
- 本机私用关闭必须附原生构建/点击、本人 Server、安全写入、恢复/备份和稳定性记录，不能仅更新文字状态；未来发布候选另需跨平台发布证据。
