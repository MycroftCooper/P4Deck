# 数据缓存与操作架构

> 文档编码：UTF-8。代码位于 `src/shared/cache/` 与 `src/app/actions/actionCatalog.ts`；本文是这两处代码的设计依据，改代码先改这里。

## 目标

1. 任何页面打开时先显示本地已有数据，不等 P4 返回；第一次冷读之外，页面打开不应出现空白等待。
2. 后台刷新永远不冻结 UI，也不清空已显示的行；刷新失败保留旧数据并显示错误。
3. 服务器只在值得问的时候被问：数据过期、用户主动刷新、操作改变了它、或自动刷新轮到了当前可见页。
4. 操作分成两类并在代码里显式标注：后台异步操作（立即开始、完成后局部刷新）与同步阻塞操作（必须拿到新鲜服务器状态才允许继续）。
5. 全部缓存只服务展示。写操作永远经后端复核真实 P4 状态，缓存错了最多显示旧行，不会写错东西。

## 与 P4V 的对照

| P4V 行为 | P4Deck 对应实现 |
| --- | --- |
| 打开 Pending/Submitted 等视图先显示上次结果，再按 `Check server for updates every n minutes` 刷新；0 表示关闭 | `useSnapshotQuery` 先渲染快照再后台重验；`UiPreferences.autoRefreshMinutes` 默认 5，0 关闭 |
| 定时刷新只刷新当前显示的视图，其他视图在切回时刷新 | `autoRefresh.ts` 先 `markSnapshotsStale()`（全部标记过期、不发请求），再只对 `activePage` 广播 `p4deck:auto-refresh`；其他页在 `p4deck:view-activated` 时发现过期才重验 |
| 列表按批次取（changelists / depot 目录的 batch size），不一次拉完 | Pending 每 100 个编号 CL 批量 `describe -s -m 1`；Submitted、Stream Graph、Branch Mappings 用 cursor 分页，Submitted `MAX_SCAN` 5000 |
| 显式刷新按钮强制问服务器 | `view.refresh` / `refresh` 命令 → `invalidateData(ALL_DATA_DOMAINS)`，仍然保留旧行直到新数据到达 |
| 每个操作的命令和输出按操作分组记录在日志窗格 | 底部 Operations 面板按 operation ID 展示；页面内只放转圈 / 绿勾 / 红叹号 |
| Pending 搜索和排序在客户端完成 | Pending 筛选、排序、展开全部读内存快照，不发 P4 请求 |

参考：P4V Server 首选项（刷新间隔与批次大小）与 `p4 changes` 命令参考，见文末链接。

## 缓存层

### 唯一的 QueryClient

`appCache`（`src/shared/cache/appCache.ts`）是进程内唯一的 `QueryClient`；`workspaceCache` 只是它的别名。一个页面刷新或一次失效必须能到达所有展示同一份 P4 数据的页面，第二个 QueryClient 会让这个前提失效（`rg 'new QueryClient' src` 必须只命中 `appCache.ts`）。

### 新鲜度分类（`policy.ts` 的 `CACHE_POLICY`）

| 类别 | key 前缀 | staleTime / gcTime | 典型数据 | 规则 |
| --- | --- | --- | --- | --- |
| snapshot | `["snapshot", domain, scope, ...params]` | 5 min / 30 min | Pending、Submitted、Workspaces、Streams、Stream Graph、Branch Mappings | 别人也能改的服务器列表；先显示再重验，页签关闭后快照继续保留 |
| target | `["target", ...]` | 60 s / 10 min | 单个文件或 CL 的 History、Diff、Revision Graph、Shelf 详情 | 围绕一个选中目标的数据；切回页签过期才重验 |
| immutable | 调用方自定 | ∞ / 30 min | 固定 revision 之间的 diff、固定版本内容 | 内容按版本寻址，永不过期，只受 GC 控制 |
| local | `["workspace-directory", stableScope, path]`、`["local", ...]` | 30 s / 60 s | 工作区目录名、本地能力探测 | 先显示磁盘/IPC 已有结果；工作区目录重开复用短期结果，磁盘发生变化时手动刷新或后台状态刷新会带回新条目 |

`SnapshotDomain` 固定为 `pending | submitted | workspaces | streams | streamGraph | branchMappings`。

### 作用域（scope）与代次（generation）

- `serverScope(runtime)` = mode + profile + server + user：Workspaces、Streams、Submitted 等“一个用户在一个服务器上能看到的数据”。
- `workspaceScope(runtime)` = serverScope + client + cwd：Pending、工作区相对视图。
- key 里**不含** `contextGeneration`。重启、重连后同一连接复用同一份快照，这正是“重启后不等 P4”的来源。
- generation 只用来**守门**：带 cursor 的页（Submitted、Stream Graph、Branch Mappings）把 cursor 绑定到 generation，重连后丢弃 cursor（`hasMore:false`）从第一页重新取；后端快照 cursor 同样绑定 connection 指纹与 generation。

### 持久化（`persistentStore.ts`）

- IndexedDB 库 `p4deck-cache`，单 store `entries`，条目带 `schema` 与 `updatedAt`；写入合并后在 `requestIdleCallback`（2 s 超时兜底）内落盘。`flushPersisted()` 立即冲刷，不等待空闲回调，并串行处理重叠写入；页面隐藏、pagehide 和开发热更新时也尽力冲刷。异常退出仍不能保证保存最后一笔尚未完成的事务。
- Pending、Workspaces、Streams、Submitted、Stream Graph、Branch Mappings、工作区目录、工作区状态和 Depot 目录均保存展示快照。工作区/Depot 快照 key 会剥离运行时 view/context generation，保留 profile 与完整 Context 指纹；同一工作区重启后可以复用，切换连接或工作区不会串数据。三个分页页面使用 `writePagedSnapshot`：内存保留当前 cursor，磁盘保存已加载的所有行、统计与查询条件，移除 `nextCursor` 并关闭续页标志。重启后的列表恢复与服务器分页会话恢复分开处理。
- 只有通过 `persist` 校验函数的数据才会被加载（`hydrateSnapshot`）；校验失败、schema 不符、别的连接的数据一律忽略。
- 没有 IndexedDB（单测、受限环境）时退化为纯内存，不影响功能。
- 持久化**只加速显示**。任何写操作都由后端读取真实 P4 状态复核，所以旧快照最多造成一次“先显示旧行再被替换”。

## 读取流程：hydrate → render → revalidate

`useSnapshotQuery({ key, enabled, fetch, persist?, staleTime? })` 是所有快照页面的统一读取入口：

1. **hydrate**：内存没有时从 IndexedDB 加载一次（`hydrateSnapshot` 去重并发加载）。
2. **render**：有数据立即渲染；`initialLoading` 只在“完全没有可显示的数据”时为 true，这是页面唯一允许显示加载态的时刻。
3. **revalidate**：数据过期（`isFresh` 为 false）才在后台 `fetch`；期间 `refreshing` 为 true，页面保留旧行，只在角落显示转圈。
4. 失败：`error` 有值但 `data` 不变；页面在旧行上方显示 `role=alert`，不得清空列表。
5. 取消：`fetch(signal)` 必须把 `AbortSignal` 传到后端，连接切换、页签卸载时整组 P4 子命令随之取消；迟到结果受 request generation / owner 保护，不能覆盖更新的状态。

没有走 `useSnapshotQuery` 的页（Submitted、Stream Graph、Branch Mappings 自己维护 cursor 与累计集合）遵循同样的三步：挂载先 `readSnapshot`；内存缺失时 `hydrateSnapshot(key, validator, { revalidate: true })` 从 IndexedDB 恢复。校验行结构、查询参数和连接身份后先渲染已加载的所有行，再在后台读取第一页和有效 cursor。磁盘恢复必须标记过期，即使 `updatedAt` 仍在新鲜窗口内、重启后的 generation 数字恰好相同，也不能复用旧分页会话。内存命中且新鲜时继续零请求复用。异步恢复受 effect 的存活标记保护；切换过滤器、连接或卸载后，迟到的磁盘结果不能更新当前页面。首屏和每次追加分页成功后都调用 `writePagedSnapshot`。

### Workspace / Depot 资源树

Workspace 和 Depot 共用 `useResourceTree` 的虚拟树与展开状态，但使用不同数据源：

1. Workspace 同时启动 `listWorkspaceChildren(..., localOnly=true)` 与带 P4 状态的查询；本地文件系统负责目录名、目录/文件类型和修改时间，P4 状态只负责补充 revision、CL、打开状态等证据。本地结果先到就先显示，P4 失败也不会擦掉本地节点。合并时以当前本地目录为权威路径集合，再按路径叠加 status：新增/未跟踪本地文件保留，已经从本地删除的文件不会被旧状态行复活。
2. Workspace 的本地目录和状态查询分别缓存、分别校验。任一查询有旧数据时，后台 `isFetching` 不产生占位行、不禁用树或刷新整页；只有“完全没有可显示数据”时才显示 loading notice。
3. Depot 没有权威本地路径。展开时先从 IndexedDB 读取该路径的上次快照并立即绘制，再按正常 freshness 后台请求 P4；旧快照刷新失败时保留节点，失败信息作为 warning 呈现。
4. 每次展开只观察当前可达路径。收起父目录会取消 React Query observer，本地 IPC 和状态查询都带 operation token；迟到结果不能把已收起目录重新展开。
5. 操作后的 `workspace-files` / `workspace-directory` / `depot-files` 失效统一使用剥离 generation 的稳定 scope；有 P4 确认的 `affectedPaths` 时，只失效根目录、路径的祖先目录和可能受目录变更影响的子目录查询；文件命令还会把选中节点的本地路径别名并入同一集合，使 Workspace 本地缓存与 Depot 缓存都命中。无路径证据时才退回该 scope 的广域失效。UI 更新仍使用原 `connectionKey` 隔离旧连接和迟到响应。

## 刷新触发

| 触发 | 入口 | 行为 |
| --- | --- | --- |
| 挂载 | `useSnapshotQuery` / 页面 `restore` | 内存快照新鲜 → 不发请求；过期 → 后台重验；分页页面从磁盘恢复 → 先显示、后台建立新的分页会话；无任何快照 → 冷读并显示加载态 |
| 页签激活 | `usePageNavigation` 广播 `p4deck:view-activated`，`useViewRefresh(page, key, refresh, staleTime?)` 监听 | 只有该页过期才重验 |
| 自动刷新 | `autoRefresh.ts`：`markSnapshotsStale()` → `p4deck:auto-refresh`（仅当前 `activePage`）；Pending/Submitted 另有 `p4deck:pending-refresh` / `p4deck:submitted-refresh` | 不可见、离线、暂停或未到间隔都不触发；进行中的读取合并重复触发；Submitted 对 `useViewRefresh` 传 `automatic:false`，避免一次心跳发两次请求 |
| 手动刷新 | `refresh` 命令 / `view.refresh` | `invalidateData(ALL_DATA_DOMAINS, { connectionKey })`；已挂载的页面立刻后台重验，未挂载的页面保留快照、下次打开时重验 |
| 操作完成或失败 | `invalidateData(actionSpec.effects, { connectionKey, affectedPaths })` | 见下一节；这是**唯一**的操作后刷新入口 |
| 连接 / 工作区 / Stream 切换 | barrier 类操作 | runtime 变化让 scope 变化，所有页面自然切到新 key；旧 key 的快照留在缓存里等 GC，切回来还能用 |

`useViewRefresh` 的 page 参数必须用 `src/app/panels.ts` 的小写 PageId（`pending`、`submitted`、`workspaces`、`history`、`streams`、`streamgraph`、`branchmappings`、`diff`、`revgraph`、`files`、`search`、`preview`、`shelf`、`settings`、`terminal`、`p4log`），写错不会报错但永远收不到事件。

## Pending 的单一所有者

Pending 是最常被操作改写的数据，所以它的快照有一个 App 级所有者：`usePendingCacheSync(runtime, connectionKey)` 在 `App.tsx` 挂载**一次**，负责 hydrate、监听 `pending-refresh` / `view-activated` / `pending-mutation` / `workflow-result`，页签关闭时照样把操作结果合并进快照。视图只用 `usePendingCache(runtime, enabled)` 读；选择器（签出时的目标 CL 选择）用 `cachedPendingChanges(runtime)` 直接取快照，没有快照或快照过期且没有编号 CL 时才退回 `queryAllPendingChanges`。

操作结果合并（`updatePendingChanges`）遇到正在进行的读取时先取消再写入、再失效重读，保证旧读取不会覆盖更新的操作结果。

## 启动与连接检查

- `useRuntime` 的 `runtimeInfo()` 仅用于初始化尚在 `loading` 的运行时。React StrictMode、Fast Refresh 或 effect 重新挂载时不得把它的旧 `notTested` 结果覆盖到已经验证的状态上。
- 连接检查按连接绑定、运行时 revision 和重试次数去重。同一请求可重新订阅；revision 已变化且仍未验证时必须重新检查。旧连接、旧 revision、旧重试的迟到结果均不得覆盖新状态。
- 自动执行 `testConnection` → `queryLoginStatus`，完整流程最多等待 45 秒。超时进入可重试的 `networkError`，不无限转圈；恢复网络、返回窗口、手动刷新或“重试连接”可发起下一次检查，进行中的检查不重复启动。
- Pending、Submitted、Files、Workspaces、Streams、History、Diff、Rev Graph、Stream Graph、Branch Mappings 在运行时配置加载后就挂载并恢复缓存，不受全页连接检查提示阻挡。页面保留旧行与搜索/展开状态；连接验证成功后，只有数据过期或用户主动刷新时才在后台查询 P4。验证失败时缓存仍可浏览，依赖远程的写操作保持禁用。

## 操作分类

`src/app/actions/actionCatalog.ts` 给每个命令一个 `ActionSpec { mode, effects }`，`satisfies Record<CommandId, ActionSpec>` 保证新增命令必须登记。

| mode | 用户视角 | UI 规则 | 当前成员 |
| --- | --- | --- | --- |
| background | 后台异步：点了就开始，UI 继续可用，完成后局部刷新 | 页面不弹窗、不显示进度条；按钮转圈 → 绿勾 / 红叹号，细节在底部 Operations | checkout、add、delete、revert、revertUnchanged、moveFiles、refresh、cancel、createChange、editChange、deleteChange、editSubmitted |
| confirm | 同步阻塞：弹窗里的预检必须拿到**新鲜**服务器状态，用户确认后才执行 | 预检期间弹窗显示加载态，这是唯一允许等待 P4 的读取；确认执行后回到 background 规则 | getLatest、getRevision、rename、lock、unlock、resolve、shelve、submit、unshelve、deleteShelf、branchMapping |
| barrier | 切换所有页面绑定的连接 / 工作区 / Stream | 切换期间页面显示旧数据或空状态，完成后全部 scope 改变 | switchStream、switchWorkspace、connection |
| view | 打开页面或系统程序，不写 P4 | 直接打开，不刷新任何服务器快照 | diff、history、revgraph、preview、reveal、openWith |

`effects` 是操作完成（成功、部分成功或失败都算）后要失效的 `DataDomain` 集合：六个 `SnapshotDomain` 加 `workspaceStatus`（`["workspace-files", key]` 与 `["workspace-directory", key]`）、`depot`（`["depot-files", key]`）、`localCapabilities`。文件类操作用 `fileState = pending + workspaceStatus + depot`，submit 再加 `submitted`。操作结果带 `affectedPaths` 时，CommandBar 把它传给 `invalidateData`，只为可能包含这些路径的目录快照创建后台刷新；没有路径或批量部分失败时使用广域失效。

P4 确认 mutation 成功的那一刻，CommandBar 先写入完成反馈并清掉当前 operation spinner；缓存失效、页面后台重验、selection reconciliation 和 `resolveSelection` 都在这之后启动。后台刷新失败不得把已经确认成功的 mutation 改成红色失败状态。未确认的 mutation 错误仍按部分成功规则提示，并触发保守的失效。

判断一个新操作属于哪类：

- 它会不会因为服务器状态与本地显示不一致而做错事（覆盖别人的锁、提交错文件、丢本地修改）？会 → confirm，预检在对话框内读新鲜状态。
- 失败能不能通过 Operations 面板的日志理解和重试？能，而且做错的代价只是“再做一次” → background。
- 它改变的是 runtime（连接、工作区、Stream）而不是数据？→ barrier。

## UI 反馈规则

1. 页面主体只在 `initialLoading` 时显示加载态；其余一律显示旧数据。
2. 后台重验用角落的小转圈（`refreshing`），不改变布局高度；禁止顶部进度条、禁止全屏遮罩。
3. 操作进度不在页面里堆文字。按钮本身转圈，完成绿勾、失败红叹号，详细信息去底部 Operations。
4. 刷新失败在旧行上方放一条 `role=alert`，附手动刷新；不自动无限重试（只读任务的重试规则见 `shared/lib/retry.ts`）。
5. 分页 cursor 过期或失效时保留已显示的行，静默从第一页重取；不显示“分页已过期 / 从第一页重新加载”提示、不弹窗。每次失败的续页至多恢复一次；恢复第一页也失败时显示真实网络或权限错误并保留旧行，不自动循环重试。后端返回重复、不前进的 cursor 属于协议异常，仍停止续页并保留诊断信息。

## 后端配套规则

- `runner.rs`：每个服务器最多 `MAX_P4_PROCESSES_PER_SERVER = 4` 个并发 p4 进程，mutation 信号量为 1；后台刷新不会把写操作挤掉，也不会让 UI 等一个被占满的队列。
- Pending 冷读把 pending / opened / shelves 三项并发读取，编号 CL 每 100 个一批 `describe -s -m 1`；绝不对 `//...` 做无界扫描。
- Submitted 查询硬上限 `MAX_SCAN` 5000，无作用域查询用裸 revision range（`command.rs` 的 `query_scope`），避免 `maxscanrows` 错误；cursor 绑定 query + connection 指纹 + generation。
- Stream Graph / Branch Mappings 后端分页快照 `SNAPSHOT_TTL_MS = 120_000`，一次性 cursor，越界或篡改即拒绝。
- 审查类读取（History / Diff / Graph / Shelf）走 Rust `ReviewCache`：30 s TTL、128 项上限，任何 mutation 后清空；operation group 取消后结果不进缓存。
- 全部读取都接受 operation token，前端 `AbortSignal` 能取消整组子命令。

## 新增页面或操作的检查清单

新增一个展示服务器数据的页面：

1. 选类别：会被别人改的列表 → snapshot（需要时在 `SnapshotDomain` 加域）；围绕一个目标 → target；按版本寻址 → immutable；本地 → local。
2. 用 `snapshotKey(domain, serverScope|workspaceScope, ...params)` 造 key，params 里放会改变结果的查询条件（已 JSON 序列化）。
3. 用 `useSnapshotQuery` 读；需要持久化就提供 `persist` 校验函数。自己管 cursor 的页按“读取流程”一节恢复快照，用 `writePagedSnapshot` 保存，禁止将服务器 cursor 直接落盘。
4. 调 `useViewRefresh(pageId, key, refresh)`；若页面已经监听自己的域事件，传 `{ automatic: false }`。
5. 在 `actionCatalog.ts` 为影响它的操作补 `effects`。
6. 测试：复用缓存不发请求、过期后台重验保留旧行、失败保留旧行、重连后 cursor 丢弃。持久化必须用真实 IndexedDB 和 `page.reload()` 回归；只改变 URL hash 不会清掉 JS 内存，不能证明重启恢复。新增的 `tests/browser/paged-snapshot-persistence.spec.ts` 覆盖三个分页页面已加载多页后重载、P4 请求挂起期间显示全部缓存、刷新失败后保留以及重试成功后替换。单测环境由 `src/test/setupCache.ts` 统一 `appCache.clear()` 并把通知调度改成微任务。

新增一个操作：

1. 在 `commandActions` 或 `pageActions` 登记 `mode` 与 `effects`。
2. mutation 得到 P4 确认后先完成 UI 反馈，再在后台 `invalidateData(spec.effects, { connectionKey, affectedPaths })`；刷新不阻塞成功反馈。若结果缺少路径，省略 `affectedPaths` 以执行保守的广域失效。
3. background 模式不加确认弹窗；confirm 模式的预检必须显式读新鲜状态并与一次性 token / digest 绑定。
4. 页面内只放转圈 / 绿勾 / 红叹号。

## 反模式

- 再建一个 `QueryClient`，或页面自己用 `useState` 保存服务器列表而不写进 `appCache`。
- 刷新前 `setRows([])`、或用全屏加载态覆盖已有结果。
- 组件挂载时 `await backend.xxx()` 之后才渲染。
- 搜索框每个字符触发一次 P4 查询；本地能过滤的数据必须在客户端过滤。
- 在 key 里放 `contextGeneration`（重启后永远 miss）。
- 操作结束后手写 `window.dispatchEvent(new Event("p4deck:xxx-refresh"))` 而不是走 `invalidateData`（Pending 自身的错误恢复路径除外）。
- 对 `//...` 或整个 depot 做无界 `p4 files` / `p4 changes`。
- 把持久化快照当作写操作的依据。

## 已知限制

- Depot 第一次冷读且没有任何快照时仍需等待 P4；Workspace 冷启动可以只等本地目录 IPC，不等待 P4 状态。两者都只能靠分批、缓存和并发缩短后台 enrich，不能凭空生成未缓存的服务端目录。
- Search 与 Shelf 详情是按需查询，不做快照持久化。
- Submitted、Stream Graph、Branch Mappings 的展示快照跨重启保留；cursor 不跨重启。Stream Graph / Branch Mappings 的后端分页快照有效期为 120 s，Submitted 的 cursor 绑定查询及连接代次；失效时全部静默重取第一页。重启后台刷新完成后，展示集合以新的第一页为准，继续加载使用新的 cursor。
- 工作区侧的 Diff（任一侧为本地文件）`reviewStaleTime` 为 0，每次激活都后台重验：本地文件随时可能被编辑器改掉，这里选择正确性；UI 仍保留旧内容，不会闪空。

## 修订图聚焦查询（2026-10-27，GRAPH-01）

- 真问题是单文件修改到目标的证据查询及反向来源追溯。复用 RevisionGraph 节点/边与唯一 appCache，不新增服务器索引或递归全库扫描。图边不等于内容包含；from 范围属于来源，into 范围属于目标，禁止混用。
- 新概念仅两个：纯图投影（路径/轨道，不产生请求）与共享图读取（缓存/并发去重/取消）。所有原始记录保留；隐藏只影响显示。既有 FileReviewPage、节点 Diff 与 CL 详情保持契约。
- 图读取按 mode、完整连接 scope、身份、profile、代次、文件、页大小及 cursor 隔离；缓存 60 秒，旧数据仅展示。权限变化由连接代次/显式刷新重验，不能从缓存证明当前未合入。内存缓存不跨身份持久化。
- 每页签每次调查最多 20 次读取尝试，100 revision 一批，现有后端 2,000 revision 上限；最多 2 个并行共享读取，不自动追溯/轮询。每次新增目标/引用/分页均显式触发。手动刷新重置调查、强制读取，取消/切换使迟到响应失效；共享请求仅最后一个订阅者取消才取消后端。
- 本轮优先单文件，输入目标是完整 depot 文件路径，不猜 branch root 映射。结论只报告集成记录证据与未知，不承诺内容仍存在；忽略、回退、缺范围、权限、分页/截断与缺节点均需展示。CL 编号仅为节点元数据；整个 CL 必须后续逐文件查询汇总，不外推。
- 守门结论：采用现有数据与有界派生视图，可以实施；对现有图 UI/缓存调用与回归断言有影响，Diff 请求契约不变。真实假服与可视验收仍受既有安全条件限制。
