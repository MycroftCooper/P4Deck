# 后端解析、IPC、缓存与兼容性性能基准

日期：2026-10-09。

## 命令与产物

```powershell
pnpm test:perf:backend
```

该命令只在显式启用 `backend-perf` Cargo feature 时构建独立 release harness，不进入默认 `cargo test`。它使用固定 seed、7 轮 warmup 和 25 轮测量，直接复用生产 `changelists::parser`、`file_service::status_snapshot`、domain serde、`StatusCache`、版本化 cursor/fingerprint 以及 Global Search 匹配/去重路径，并生成：

- `artifacts/performance/backend-latest.json`：机器可读环境、兼容性清单、p50/p95、payload 大小、RSS 采样和正确性门禁；
- `artifacts/performance/backend-latest.md`：同一次运行的可读摘要。

产物与前端性能报告一样位于 Git 忽略目录，避免将不同机器的波动值混入源码。实现没有引入独立算法或大型 benchmark 框架；仅将生产文件状态转换函数收窄为 crate 内可见，并从 Global Search 服务提取已有去重语句供生产调用与基准共用。

## 阈值与门禁

项目现有 `<50 ms` 数值目标明确针对 50,000 条前端本地筛选反馈，不能移植为后端解析、serde、缓存或 cursor 的 PASS 标准。因此本报告所有时延均为**信息项**，专用命令只用以下确定性断言阻止回归：

- Submitted/Pending/File 条目数、顺序与分类；
- 10k/50k/100k IPC payload 的 serde round-trip；
- 状态缓存 TTL、512 容量 LRU、相同并发请求合并和范围失效；
- Submitted/Pending cursor 版本、查询、连接及双 generation 绑定和错配拒绝；
- Unicode 匹配范围与稳定 identity 去重。

普通 `cargo test` 不执行易波动的计时门禁。

## 内存口径

JSON 报告记录每个 case 测量前后的进程 RSS；本次最大边界增量为 File status 解析约 `70.80 MiB`。Windows 同时读取 `PeakWorkingSet64`，本次整个进程运行期间最高为约 `251.19 MiB`。这两个数值都不是分配器级别或单 case 的精确峰值：RSS 会受预先构造的数据集、分配器复用和 GC 不存在等因素影响；`PeakWorkingSet64` 是从进程启动后累计的全局峰值。它们只用于发现明显的无界增长，不能冒充固定设备内存认证。

## 本机兼容性清单与矩阵边界

- 实际执行的 `p4 -V`：`P4/NTX64/2023.1/2442900 (2023/05/15)`；
- 实际执行的 Fixture `p4d -V`：`P4D/NTX64/2026.1/3062361 (2026/09/08)`；
- 实际读取的本地客户端设置：`P4CHARSET=utf8`；
- 未连接服务器，因此 server Unicode mode 为**未验证**；本地 `P4CHARSET` 不等同于 Unicode Server 认证。

版本矩阵执行时可分别设置 `P4DECK_P4_PATH` 与 `P4DECK_P4D_PATH` 后运行同一命令，并把两份 `backend-latest.*` 复制为带平台/版本/Unicode 模式的独立证据。只有实际完成对应 server handshake/E2E 后，才能在矩阵中标记 Unicode/non-Unicode、Proxy/Broker 或 SSL 通过。

本机合成数据不证明 macOS、其他 P4/P4D 版本、真实 server 输出差异、原生 Tauri IPC 峰值、代理/SSL 或长时间稳定性。生产当前使用 `-Mj` JSON Lines；ztag 与 `p4 -I` 尚未完成多版本兼容矩阵，未默认启用，也未在本报告中宣称通过。
