## 已确认的证据与缺口

- 通过文件 SHA-256 检查，`.local/p4d-fixture/bin/p4.exe` 与 `p4d.exe` 均匹配 fixture 脚本内固定哈希；未执行二进制。磁盘 `server/server.id` 为 `p4deck-fixture-local`。这只能证明本地文件，不能证明端口上的实际服务身份或无代理。
- fixture 脚本指定 `127.0.0.1:16661`、项目内 server/workspace/tickets/trust/p4enviro 路径和 fixture user/client；P4 调用显式传入 `-p/-u/-c`。
- 修复前 `Assert-RunningServerIsFixture` 通过 `Get-FixtureServerId` 执行 `p4 info` 后才判断 server ID；`status` 也可能走此路径。修复后，P4 调用前先执行环境与 OS listener 门禁，但 `status` 仍可能在通过门禁后发起 P4 查询，不能作为纯静态检查入口。
- `Invoke-WithFixtureEnvironment` 移除进程 `P4CONFIG` 与 `P4PASSWD`；修复后新增前置拒绝继承设置的门禁，但没有据此宣称所有配置来源都已隔离。生成的 `env.ps1` 也不是完整的凭据隔离证明。不得直接 dot-source 并据此认为安全。
- 本轮进程环境未发现 `P4*` 变量，但本机注册表存在 P4 连接、P4CONFIG 和凭据配置项。未读取或记录凭据值。进程环境为空不等于全局配置为空。
- QA 配置仅覆盖应用标识和窗口。`ContextStore::load` 加载 `connection.json`，缺失时使用 `environment_context()`；后者读取进程 P4 环境。应用还在连接加载前应用待恢复备份。因此必须核验 QA 已保存连接、待恢复配置和环境回退，不能只确认“QA”窗口标题。
- 操作系统只读 listener 检查 `Get-NetTCPConnection` 返回 CIM `PermissionDenied` / `HRESULT 0x80041003`。当前不能确认 16661 的占用进程及其启动参数，不能把无输出解释为端口空闲。没有提升权限或修改系统策略。

## 后续运行的放行条件

1. 在任何 P4/TCP 探测前，通过受支持的本地只读诊断核对 listener 所属进程、二进制、启动参数、server root，以及服务配置不含生产代理、转发或复制目标；无法证明则不连接。
2. 核对当前进程、用户/系统环境、Windows P4 注册表、P4CONFIG 查找链、P4ENVIRO 和默认凭据路径。记录是否隔离与路径归属，不输出秘密。不能只删除环境变量来声称隔离完成。
3. 对 QA 应用确认持久化 Profile、恢复队列、CLI 路径、Server/User/Client/Root、tickets/trust 均属于此 fixture；启动 fixture 的子进程环境不会自动传回随后启动的 Tauri 父 shell。
4. 核验失败时只继续文件阅读、脚本语法检查等无连接工作；不得用 `p4 info`、`login -s` 或 fixture `status` 来试探未知端点，不修改全局配置来规避。

这些前置尚未全部满足，因此本轮没有运行 fixture、桌面应用、P4 E2E 或生产连接。WIN-P0/P1/P2 的既有验收状态保持原口径；本文只完成安全入口的文档核验，不关闭原生/集成/稳定性验收项。
