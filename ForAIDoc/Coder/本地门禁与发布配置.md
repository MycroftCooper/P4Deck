# P4Deck 本地门禁与发布配置

> 2026-10-29 改造后：未使用的 release/updater 骨架已按用户决定删除（见「发布与更新器」），本文只描述当前本地门禁与发布边界。2026-10-27 的执行限制仍然适用：只运行经审计且获准的定向检查，不直接执行全量 test/ci 或 fixture 入口，不使用 ExecutionPolicy Bypass 规避既有拒绝。用户新增授权的定向 Windows 体验包见[Windows体验包交付](Windows体验包交付.md)及唯一 TODO 的 PKG-01。

> 当前事实：代码与发布都在 GitHub（`MycroftCooper/P4Deck`），但门禁仍是本地三层（见下一节），没有远端流水线。CI 是代码质量检查工具，不是 Perforce 功能；它不会连接用户的 P4 Server。

## 日常本地验证

开发完成后先运行：

```powershell
pnpm ci:quick
```

该命令默认并行跑两组。Web 组按固定顺序执行：前端契约检查、版本一致性校验及其测试、`ci-step-result` 协议测试、版本测试、主题对比测试、Prettier（现在也检查 `scripts/*.mjs`）、TypeScript（`tsc -b`）、前端 Vitest（用 `test:web:ci`，即 `vitest run --reporter=dot` 降噪），最后跑浏览器冒烟子集（`page-smoke`、`workspace-switcher`、`sidebar-resize`，约 35 秒）；Rust 组执行 rustfmt、Clippy（`--all-targets -D warnings`，不再单独跑 `cargo check`）和 `cargo test --quiet`（存在工作流状态库时还会先跑 `workflow-state`）。

浏览器测试由 Playwright 自己启动或复用 `127.0.0.1:1420` 的 dev server，门禁本身不做服务器管理；它会真实渲染界面，是唯一能发现“页面打不开/菜单点不到”这类问题的检查。

`quick` 默认失败不中断（`--continue`）：一次跑完所有步骤再汇总，方便 AI 修复循环一次拿到全部失败点，减少反复重跑。默认安静模式只把每步一行 `✓/✗ 名称 耗时`、失败摘要（如“未格式化文件 N 个: a,b…”）和最后一行 `{ok,mode,durationMs,failed,summary}` 紧凑 JSON 打到 stdout；完整子进程输出写入 `artifacts/ci/logs/quick/<step>.log`，机器可读摘要写入 `artifacts/ci/quick-latest.json`（含每步 name/status/exitCode/durationMs/logPath）；摘要不收集环境变量或凭据。

所有模式共用以下选项：

- `--continue` / `--fail-fast`：跑完所有步骤再汇总 / 遇错即停（`quick`、`bundle` 默认 `--continue`，`local` 默认 `--fail-fast`）。
- `--verbose`：不捕获输出，直接把子进程完整输出打到终端，用于排查。
- `--serial`：关闭 Web/Rust 并行，全部串行。
- `--timeout-ms <毫秒>`：单步超时，默认 900000（15 分钟）；超时会杀掉整个进程树并判该步失败。
- `--files a,b`：传入本次改动文件；若全是 `.md`/`.txt` 或 `ForAIDoc/` 下的文档，直接判定 docs-only 并成功退出，不跑代码门禁。
- `--json`：stdout 只输出紧凑 JSON 摘要。

### 快速自检：ci:bundle

改动涉及打包或前端 mock 时，可先跑约 10 秒的快速自检：

```powershell
pnpm ci:bundle
```

它只跑版本一致性校验、`pnpm build:desktop` 和 `pnpm validate:bundle`，适合“改打包/前端 mock 相关后快速自检”；它不替代交付前的 `pnpm ci:local`。

发布候选前可运行：

```powershell
pnpm ci:local
```

它先并行跑上面的 quick 基础组，全部通过后再串行追加：浏览器 `pnpm build`、桌面 `pnpm build:desktop`、`pnpm validate:bundle`（断言 `dist` 中不含 mock backend 代码）、**完整浏览器测试套件（`tests/browser` 全部 spec，约 8 分钟）**、前端性能门禁和后端 release 性能门禁，避免多个重任务同时争用机器或改写同一份性能报告。`local` 默认 fail-fast（遇错即停），需要一次拿到全部失败点时加 `--continue`。Windows 隔离 `p4d` E2E 默认不执行；明确需要时使用：

```powershell
$env:P4DECK_CI_RUN_P4D = "1"
pnpm ci:local
Remove-Item Env:P4DECK_CI_RUN_P4D
```

这只允许 Windows 的项目隔离 fixture，不能连接真实 Server。显式设置 `P4DECK_CI_RUN_P4D=1` 后，P4D 门禁属于“必跑”：缺少固定版本的 `p4`/`p4d`、fixture 脚本、Cargo 或项目清单都会非零失败，不会显示成通过。项目不会在门禁里自动下载二进制；本地可先人工运行 `pnpm fixture:setup:win` 准备经过哈希和签名验证的工具。

P4D 脚本和本地门禁使用稳定的 JSON 结果协议，不解析人类日志。摘要中的状态含义如下：

| 状态      | 含义                                                                                                         |
| --------- | ------------------------------------------------------------------------------------------------------------ |
| `passed`  | 步骤确实执行完成且退出成功；P4D 还必须返回合法的成功协议结果。                                               |
| `failed`  | 步骤非零退出、结果协议缺失/非法，或执行/清理失败；总体门禁失败。                                             |
| `skipped` | 仅表示可选的 P4D 检查因 fixture 前置条件缺失而未执行，绝不等于通过；若调用方已显式要求 P4D，总体门禁仍失败。 |

直接运行 `pnpm test:e2e:p4d:win` 而未要求必跑时，缺 fixture 会以 `skipped` 收口并保持零退出，方便日常开发；`ci:local` 显式选择 P4D 时会自动切换为严格模式。

## 远端流水线（仍不设，但发布已走 GitHub Releases）

代码仓库与发布都在 GitHub（`MycroftCooper/P4Deck`），但**不维护远端 CI 流水线**；唯一质量门禁仍是本地三层：`pnpm wf:fast`（每片开发中）→ `pnpm ci:quick`（freeze 前）→ `pnpm ci:local`（交付候选，快速自检可用 `pnpm ci:bundle`）。发布是本地命令直接调用 GitHub API，详见下一节。

如果以后确实要接入远端 CI，应另立方案并按当时需要重新设计，不恢复空壳。无论本地还是将来的远端，都遵循：不配置 secret、不自动发布、`skipped` 永不等于通过。

## 发布与更新器（现状）

> **2026-11-17 更新**：本节描述当前实际流程，替代此前“没有 updater runtime”的历史结论。自动更新自 0.1.9 起真实可用，0.1.9–0.1.14 均由本地脚本发布到 GitHub Release。

当前能力：

- 应用内自动更新已启用：`src-tauri/tauri.conf.json` 设置 `bundle.createUpdaterArtifacts: true`、`plugins.updater.requireSignedVersion: true`、`windows.installMode: "passive"`，端点指向 `https://github.com/MycroftCooper/P4Deck/releases/latest/download/latest.json`。
- `scripts/publish-update.mjs` 一条命令完成：构建 NSIS 安装包 → 校验 minisign 签名与公钥 → 生成 `latest.json` → 上传 `.exe`、`.exe.sig`、`latest.json` 三个资产并发布 release。
- 分支约定：日常提交在 `dev`，`release` 只接受 `dev` 的 `--no-ff` merge 并打 `v<semver>` tag；`pnpm wf:release --version x.y.z --apply` 只做本地 merge + annotated tag，不推送、不上传。

一次完整发版：

```powershell
pnpm release:bump --version 0.1.16 --notes-file ForAIDoc/PM/releases/v0.1.16.md
pnpm ci:quick                       # 至少这一层，发布日建议 ci:local
pnpm wf:release --version 0.1.16 --apply
git push origin dev release --follow-tags
node scripts/publish-update.mjs     # 自动使用 ForAIDoc/PM/releases/v0.1.16.md
pnpm release:verify                 # 发布后匿名核验，产出 verify-0.1.16.json
```

关键约束（都是为避免重蹈覆辙）：

- **发布说明必填**：`publish-update.mjs` 不再允许空正文。未传 `--notes-file` 时会自动读取 `ForAIDoc/PM/releases/v<version>.md`；两者都没有则直接失败。空正文曾导致应用内更新提示空白。
- **发布说明入库**：notes 文件放在 `ForAIDoc/PM/releases/` 并提交，不再只躺在被忽略的 `artifacts/`。
- **版本号一处改**：`pnpm release:bump` 一次同步 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`，并根据 notes 文件自动生成 `src/app/update/changelog.ts` 的新条目，最后跑 `validate:versions` 与 `validate:changelog`。拒绝降级或重复版本。
- **发布后核验可复现**：`pnpm release:verify --version x.y.z` 匿名复核 `releases/latest` 指向、资产清单、公开 `latest.json` 与安装包字节、签名 keyId 与签名内的版本号，报告写入 `ForAIDoc/PM/releases/verify-<version>.json`。GitHub API 匿名限流时相关检查降级为 `skipped` 而不是失败，下载与签名校验照常执行。

### 本地产物入口

不发版时，本机也可以单独产出未签名候选（细节见 [Windows 体验包交付](Windows体验包交付.md)）：

```powershell
pnpm validate:versions     # package.json / tauri.conf.json / Cargo.toml 版本一致性
pnpm validate:changelog    # 应用内更新日志：版本齐全、newest-first、中英双语
pnpm build:desktop:win     # 独立 exe → artifacts/desktop/
pnpm package:desktop:win   # NSIS 安装包 → artifacts/delivery/
```

这些命令只在本机产出未签名候选，并写入 `artifact-info.json`（version、gitHead、gitDirty、size、sha256）；默认拒绝脏工作树，确需时显式加 `--allow-dirty`。它们不签名、不上传、不发布，也不构成跨设备可用证明。

### 发布说明（中英双语）

GitHub release 的正文必须是中英双语。文件放在 **`ForAIDoc/PM/releases/v<version>.md`**（入库，随代码一起评审），格式：

```
# P4Deck 0.1.16

## 中文
- ...

## English
- ...
```

- 校验：`node scripts/validate-release-notes.mjs --version <version> <file>`。
- 发布：`node scripts/publish-update.mjs` 会自动取同版本文件；缺任一语言时发布会拒绝继续，空正文同样拒绝。
- GitHub 正文：中文在上，英文折叠在 `<details>` 块里。
- `latest.json` 的 `notes` 取中文段，保持应用内更新提示一致。
- 应用内「设置 → 更新 → 查看更新日志」的数据在 `src/app/update/changelog.ts`，由 `pnpm release:bump --notes-file <file>` 从同一份说明自动生成，`pnpm validate:changelog`（已进入 `ci:quick`/`ci:local`）把关。
- 已发布 release 只想补双语正文时，用 `node scripts/update-release-notes.mjs --version x.y.z --notes-file <file>`（先加 `--dry-run` 预览；需要 `GITHUB_TOKEN` 或已存的 git 凭据），它只改正文，不动资产和签名。

## 尚未完成的外部发布验收

以下事项仍未完成，不能因为本地门禁存在就标记为通过：

- 远端 CI 流水线：当前阶段明确不做（本地三层门禁已覆盖质量检查）。
- Windows 代码签名；macOS Developer ID、Hardened Runtime 与 notarization。
- 安装包在干净设备上的安装/卸载/启动验收，以及 WebView2 联网 bootstrapper 与离线安装包两种模式的实机验证。
- 旧版本升级矩阵与失败回滚的实机验证（updater 机制已具备，缺的是跨版本实测证据）。
- 安全注入真实签名凭据，并验证凭据轮换、吊销与审计。

在这些外部证据齐全前，P4Deck 仍不可作为公开或跨平台产品发布；它们不阻塞“当前 Windows 机器本人私用”阶段，该阶段以 [Windows 本机私用 TODO](../PM/Windows本机私用TODO.md) 为准。
