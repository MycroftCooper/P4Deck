# 故障恢复与配置备份

> 文档编码：UTF-8。本文是 WIN-P1-01/02 的实现与操作依据，相关代码位于 `src-tauri/src/p4/process.rs`、`src-tauri/src/p4/runner.rs`、`src-tauri/src/persistence/operation_journal.rs`、`src-tauri/src/persistence/backup.rs`、`src-tauri/src/ipc/commands.rs` 与 `src/features/tools/components/OperationJournalView.tsx`。

## 目标

1. 网络、认证、取消、进程异常或超时发生后，界面不能把未确认的 mutation 报成成功。
2. 未确认的写操作只能由用户核对服务器状态后明确重试，应用不得自动重放。
3. 用户能在重启前后看到故障分类、关联日志和人工恢复步骤。
4. 用户能离线备份和恢复非敏感连接配置、窗口位置与布局，且写入失败不会静默留下部分恢复。
5. 凭据、日志、Journal、终端历史和可重建缓存不进入普通配置备份。

## 故障分类与恢复

| Journal failure | 典型来源 | UI 行为 | 用户恢复步骤 |
| --- | --- | --- | --- |
| `offline` | 系统离线或网络层失败 | 保留已有数据，提示连接中断 | 恢复网络、重新连接并刷新；写操作先核对服务器结果 |
| `serverUnreachable` | Server/CLI 不可达；只读请求超时 | 只读请求可重试，保留旧行 | 恢复 Server 或 CLI 后重试只读；写操作先核对 |
| `authExpired` | ticket 缺失、过期或登录失效 | 显示重新登录入口 | 登录后刷新；若中断的是 mutation，先核对再决定重试 |
| `cancelled` | 用户取消或连接代次切换 | 标记已请求取消，不宣称所有目标都未执行 | 刷新 Pending/Workspace，确认已完成部分后再继续 |
| `interrupted` | 应用执行中退出；下次启动恢复 Journal | 显示“结果未知，必须人工核对” | 查看关联日志，刷新 Pending/Workspace，再到 Server 侧核实 |
| `unknown` | mutation 已启动但超时或结果无法确认 | 显示红色人工恢复提示 | 不直接重试；核对页面、日志和 Server 实际状态后明确决定 |

只读 `p4` 命令超时归为 `serverUnreachable`；非只读或未知命令超时归为 `unknown`，因为命令可能已经到达 Server。Windows 上所有 P4 子进程都会加入设置了 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 Job Object，并以 `CREATE_NO_WINDOW` 启动；用户关闭主程序时，Windows 会回收整个 P4 进程组。超时路径也会终止并等待子进程真正退出，避免后台残留命令继续改变结果。

`OperationJournalView` 在存在需要恢复的记录时显示汇总提示，并为每条记录说明恢复范围。Journal 不保存可重放 payload，也没有“自动重试上一次 mutation”的入口。

### 人工恢复顺序

1. 在 Operations 中找到失败操作和时间，跳到关联日志确认最后执行的命令及输出。
2. 刷新 Pending 和 Workspace；只读请求失败可以直接重试。
3. mutation 结果未知时，到 P4 Server 侧核对目标 CL、文件状态、锁、Shelf 或提交结果。
4. 只有确认目标没有发生预期变化后，用户才能重新执行原操作。
5. 再次执行仍使用正常预检、确认、operation ID、Journal 和局部缓存失效流程。

## 配置备份

### 包含内容

- `connection.json`：已保存 Profile、活动 Profile、Context 和 revision；不包含密码、ticket 或 trust 内容。
- `window-placement-v1.json`：Dock panel 和工具窗口位置。
- `localStorage` 白名单：主题、语言、密度、页面、Dock/tool panel 布局、保存的筛选和日志视图偏好。

### 明确排除

- P4 ticket、SSL trust/fingerprint、密码和系统凭据。
- 终端历史、文件选择和 mock 连接数据。
- 日志、Operation Journal、诊断导出。
- IndexedDB 中的 Pending/Submitted/Stream/目录快照等可重建缓存。
- Git 仓库、测试 fixture 和备份包本体。

### Bundle 安全边界

- schema 版本固定为 `1`，反序列化拒绝未知字段。
- 包内最多两个允许的文件名，不能出现路径穿越或重复文件。
- 每个文件有 SHA-256；连接文档和窗口位置文档还要通过各自的结构校验。
- 单包上限 4 MiB、单文件上限 2 MiB；localStorage 只接受 allowlist，最多 200 键、2 MiB。
- 所有写入先落到临时文件并 `sync_all`，再原子替换目标文件。
- 损坏、被篡改或含未知文件的备份不会改动在线配置。

## 恢复流程

1. Settings → 本地配置备份读取备份列表、待恢复状态和最近一次恢复结果。
2. 选择“恢复”时，后端先验证源备份，并生成带当前在线配置与当前布局的 `pre-restore` 回滚包。
3. 后端写入一次性 `pending-restore-v1.json` 清单，记录源文件 SHA-256 和回滚包；此时连接配置尚未切换。
4. 前端只替换 allowlist 内的布局键；写不进去时明确提示保留回滚包，不再声称布局已经恢复。
5. 完全退出并重新打开 P4Deck。启动阶段在 `ContextStore::load` 之前再次校验源备份 digest 和结构并应用恢复。
6. 应用前先读取两个在线配置文件的完整旧内容。任一文件替换失败时立即恢复两份旧文件，并把恢复标记为 failed。
7. 全部成功后写入 succeeded 状态并移除 pending 清单。若进程在文件替换中途崩溃，pending 清单仍在，下次启动会幂等重做整包恢复。

回滚时选择对应的 `pre-restore` 包并重复同一流程。待恢复、失败和成功状态都显示在 Settings；回滚包本身不会被自动删除。

最终交付使用 Debug/HMR 和 loopback fixture，不构建或替换 EXE。

```powershell
pnpm dev

pnpm test:browser
cargo test --manifest-path src-tauri/Cargo.toml --lib
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-p4d-e2e.ps1 -Repeat 1
```

fixture 固定为 `127.0.0.1:16661`。故障与备份自动化覆盖：

- mutation 超时归为 `unknown`、只读超时归为 `serverUnreachable`。
- Journal 重启后把未终结操作改为 `interrupted`，且记录中没有可重放 payload。
- unknown/interrupted/cancelled/authExpired/offline/serverUnreachable 的 UI 恢复提示。
- 备份/恢复 round trip、凭据与临时状态排除、digest 篡改、路径穿越、未知文件、staged 内容篡改、回滚包、第二个文件写入失败后的双文件回滚。

2026-10-22 已在 Debug/HMR、QA Profile 和 loopback fixture 上完成 Windows Tauri 原生人工验收：

| 场景 | 原生观察 | 复核结果 |
| --- | --- | --- |
| Server 停止 | Pending 保留缓存并显示不可达错误；Journal 记录 `serverUnreachable`，没有把缓存当成成功结果 | 恢复 fixture 后可重连并刷新；写操作没有自动重放 |
| ticket 缺失 | 显示认证失效，同时保留本地缓存 | 不把认证失败伪报成数据为空；mutation 仍需人工核对 |
| 完全离线重启 | Workspace/Pending 先显示上次缓存，并明确标注离线/陈旧状态 | 没有因 P4 查询阻塞而退化为空白页 |
| 用户取消长操作 | Journal 显示 `cancelled`，提示执行范围可能不完整 | 刷新后可人工确认已完成部分，不自动重试 |
| 执行中关闭应用 | 重启后未终结操作变为 `interrupted`，显示“结果未知，必须人工核对”，没有重放入口 | 本地 fixture 的 `qa-workflow-actions.txt` 最终无 open 记录，workspace 与 Have 一致；应用退出后无残留 `p4.exe` |
| 配置备份、恢复和回滚 | 创建备份后修改连接名与主题，完全退出重开确认恢复；再选自动 `pre-restore` 包恢复，连接名和主题回到恢复前状态 | 恢复状态为 `succeeded`；手工包含连接配置、窗口位置与 26 个布局键；ticket/trust canary 命中为 0 |
| 150% DPI 窗口恢复 | 设置独立窗口逻辑位置 `300,200`、尺寸 `1000×700` 后退出重开 | 窗口文件保存相同逻辑值，WebView 报告内部尺寸仍为 `1000×700`，不再把逻辑值重复乘 DPI |

这次原生演练还修复了三个实现缺口：应用退出后孤儿 `p4.exe` 未回收、Journal 恢复时间缺少 UTC 时区导致显示偏移，以及 150% DPI 下窗口位置/尺寸按物理像素写入后越开越大。ticket 缺失由临时移除 fixture ticket 模拟，不替代本人实际 Server 的 SSO/MFA 和认证策略验收。

## 已知限制

- 普通配置备份不是 Server 数据备份，不包含 Pending 文件内容、Shelf、Submitted 数据或本地未提交源码。
- 恢复连接 Profile 不恢复外部 P4 ticket/trust；重启后仍按 Server 实际策略重新认证或 trust。
- 配置文件分属两个文件，无法依赖文件系统提供跨文件原子事务。实现通过 pending 重试、即时失败回滚和 pre-restore 包覆盖该边界。
- 如果布局 localStorage 被 WebView 禁用，连接/窗口恢复仍可继续，但布局需通过回滚包或手动设置恢复。
- fixture 的 ticket 失效验证覆盖本地失败分类和缓存保留；实际 Server 的 SSO/MFA、插件认证、权限和 trigger 仍需在本人 Server 的 P0 验收中确认。
