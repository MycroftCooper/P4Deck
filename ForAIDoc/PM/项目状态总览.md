# P4Deck 项目状态总览

> 文档角色：项目进度与范围的唯一总览入口  
> 首次建立：2026-09-29  
> 最近盘点：2026-10-08

> 发布判断：尚不可发布；真实 P4 日常工作流尚未完成闭环

## 1. PM 结论

P4Deck 已经越过“只有原型和 Mock”的项目启动阶段：桌面端真实 Backend、受控 P4 Runner、Workspace/Depot 浏览、基础文件操作、文件预览、Diff/History/Revision Graph、CL 查询及部分 CL/Shelf 命令都已有代码落点，应用壳、Dock 布局、主题和中英文界面也已成形。

当前仍属于 Alpha 工程阶段，主要原因如下：

1. 连接与认证后端已通过 Windows localhost 的强类型连接与隔离 ticket 验收，但前端连接向导和 SSL trust/SSO 生命周期尚未验收。
2. Submit、Pending 与 Shelf/Unshelve/Resolve 已完成 BE-003/BE-004a/BE-004b 前端生产接线和浏览器自动化验收；后端真实闭环与 Windows localhost E2E 也已完成，但 Windows/macOS 原生 UI 仍待验收。
3. 后端缓存、操作记录、日志策略和诊断导出基础已完成，但对应设置、状态展示和真实离线/ticket 行为尚未经过服务器验收。
4. 50,000 条合成目标已验证虚拟化和末项导航；Windows 本地 `p4d` 的 BE-002/BE-003/BE-004a/BE-004b 应用层 E2E 已通过，但 100,000 条完整性能基准、Windows/macOS 原生 UI 冒烟仍无验收记录。
5. 本地仓库已有经验证的阶段提交，但尚无 remote 与 CI，仍不能视为可恢复的发布基线。

因此，当前里程碑仍不应标记为“可供私有 Alpha 使用”。生产构建及 BE-002～BE-004b 前后端基线已恢复绿色；下一目标是完成原生流程冒烟，并建立 remote/CI。

## 2. 状态口径

| 状态 | 定义 |
|---|---|
| 已完成 | 有前后端或明确单端实现，并有自动化测试或可重复验证证据；在当前约定范围内可用 |
| 部分完成 | 已有 UI、契约或底层能力，但用户流程、异常处理、平台验证或验收证据不完整 |
| 未开始/未完成 | 没有可用实现，或只有文档规划、占位入口 |
| 阻塞 | 会阻止构建、集成、验收或发布的问题 |

功能是否“完成”以用户闭环和验收证据为准，不以文件、按钮或接口是否存在为准。

## 6. 当前项目结构与职责

```text
P4Deck/
├── src/                         React 前端
│   ├── app/                     应用装配、Dock、Shell、全局 Hook 与样式
│   ├── features/                按业务能力组织的页面和交互
│   │   ├── browsers/            Preview、Diff、History、Revision Graph、Streams
│   │   ├── changelists/         Pending 与 Submitted 工作流
│   │   ├── files/               Workspace/Depot 浏览、地址、文件动作
│   │   ├── settings/            连接、主题、语言与 UI 偏好
│   │   ├── tools/               P4 Terminal 与 Log
│   │   └── workspaces/          Workspace 列表与详情
│   ├── infrastructure/backend/  Backend 契约及 Mock/Tauri 适配器
│   └── shared/                  共享类型、i18n 和无业务归属工具
├── src-tauri/src/               Rust 桌面后端
│   ├── ipc/                     Tauri Command 边界
│   ├── app/                     应用服务与用例编排
│   ├── domain/                  领域模型
│   ├── p4/                      P4 Runner、Context 与业务 Repository/Parser
│   └── persistence/             SQLite 日志等本地持久化
├── ForAIDoc/
│   ├── PM/                      范围、路线图、状态与验收口径
│   ├── Coder/                   架构、实现说明与开发环境
│   └── Designer/                体验与界面规范
├── scripts/                     环境检查、安装辅助和本地 p4d Fixture
├── assets/                      品牌源素材
└── public/                      Web/Tauri 静态资源
```

### 结构治理规则

1. PM 文档定义“为什么做、做什么、优先级、完成标准”；技术文档定义“怎么做”；设计文档定义“如何交互与呈现”。
2. 新业务能力优先进入 `src/features/<domain>`；跨功能契约进入 `shared/contracts`；外部系统适配只进入 `infrastructure`。
3. Rust 的业务参数构造和解析放在 `p4/<domain>`；`ipc` 不承载业务规则，`runner` 不认识具体业务对象。
4. 功能状态变化先更新本文件，再同步路线图、实现说明和 README，避免多个“当前状态”互相冲突。
5. 完成项必须附验证证据；只有 Mock 演示、只有 UI 或只有底层命令时，一律记为“部分完成”。

2. 完成 100,000 条性能基准、缓存与请求治理验证。
3. 完成 Windows/macOS 实机冒烟、诊断导出与关键无障碍检查。

退出条件：满足《开发路线图》阶段 3 的私有 Alpha 条件，且不存在 P0 阻塞。

## 8. 风险与待决策

| 风险/决策 | 影响 | 当前建议 |
|---|---|---|
| 只有本地 Git 基线、没有 remote/CI | 本机可回滚，但无法证明异机恢复与平台持续集成 | 建立私有 remote，并接入 Windows/macOS CI |
| 文档描述曾领先/落后于代码 | 进度判断失真 | 本文作为状态单一入口，其他文档只保留稳定规范 |
| 功能面铺得较宽，核心闭环仍有缺口 | 容易出现“页面很多但不可日用” | 暂停新增 P2 页面，优先连接与 Submit 闭环 |
| P4 版本、服务器策略和平台差异 | Mock/单测通过不等于真实可用 | 建立版本矩阵与 localhost Fixture E2E |
| 大列表目标尚无基准报告 | 无法确认核心性能承诺 | 在 Alpha 前固定数据集、设备和测量方法 |
| 原生多窗口复杂度较高 | 可能拖慢核心流程交付 | 首个 Alpha 以稳定停靠为主，原生拖出按验收结果收敛 |

## 9. 文档维护机制

- 每次合并会改变用户可见能力的工作后，更新“功能进度台账”和“最近盘点”日期。
- 每周至少检查一次 P0 阻塞、下一执行批次和路线图阶段判断。
- 需求新增或降级时，先修改《核心功能基线》或《开发路线图》，再进入开发。
- 架构边界变化同步更新《技术架构》；实际实现范围同步更新《核心功能实现说明》；交互变化同步更新《体验与界面规范》。
- 发布候选版本必须附构建、测试、E2E、性能和双平台验收记录，不能仅更新文字状态。
